# Evaluation sets

Evaluation inputs and run records for the Wongnai review corpus
(`retail_db/wongnai_review_coll`, 40,000 rows).

| File | What | Recoverable from |
|---|---|---|
| `thai_queries.jsonl` | 100 hand-written Thai queries | **The local backup only** (below) |
| `rag_responses.jsonl` | 100 paid-for `gpt-5-nano` analyst responses to those queries | **The local backup only** (below) |
| `reviews_heldout_sample.jsonl` | 100 held-out reviews for the `assess` prompt | Regenerated byte-for-byte by the sampler |
| `runs/<RUN_SLUG>/` | One directory per eval or load-test run | Not recoverable; scores also go to MLflow |

### Untracked by design

Nothing under `data/` is in git, and that includes this directory: `.gitignore`
ignores `data` as a whole, and that is deliberate (Q1 = B in
[`implement_plan_[analyst_prompt_scoring].md`](../../docs/part_1/implement_plan_[analyst_prompt_scoring].md#step-0--q1-eval-data-stays-untracked-option-b)).
This README is not committed either; it documents this machine only.

A score is reproducible from the code plus `SAMPLE_SEED` plus `eval_set_sha`,
both logged to MLflow and to each run's `run_meta.json`. The two files that
cannot be regenerated are backed up **outside the repo**, and that backup is
the copy of record:

```
C:/Users/Kao/retail_rag_eval_backup/20261020/
  rag_responses.jsonl  sha256 9778f58cdcc1eae2c8e9f11147b80e996ce118cd8b5013f1ae6a608c528b7ef6
  thai_queries.jsonl   sha256 1b81ba31f350d73f7d55dacd6c85211f0520955bd4010324d61938f3d263e732
```

Check the live files against those hashes after any eval run -- `git status`
cannot see them, so it proves nothing. **Never `git clean -fdX`**: with `data/`
ignored it deletes everything here, and the corpus with it.

Regenerate the held-out set on a fresh machine with:

```bash
python scripts/sample_heldout_reviews.py --n 100
```

# Evaluation queries

Hand-written Thai queries. Unlike the corpus, these are **authored evaluation
assets**: the scores in [`docs/part_1/benchmark.md`](../../docs/part_1/benchmark.md)
are only reproducible if the query set is fixed, which is why they are backed up
rather than left to chance.

## `thai_queries.jsonl`

100 queries, one JSON object per line.

| Field | Meaning |
|---|---|
| `id` | 1-100, stable. The sweep evaluates prefixes, so **order is significant** |
| `query` | The Thai query string |
| `intent` | Short English gloss of what the query is looking for |
| `sentiment` | `negative` (11), `positive` (1), or `neutral` (88) |
| `in_latency_set` | `true` for ids 1-10 — the original section 3 latency workload |

### Why the order matters

Section 4 of [`notebook/eval_qa_grounding.ipynb`](../../notebook/eval_qa_grounding.ipynb) sweeps
N = 10, 20, … 100 by taking the **first N** queries. The list is therefore
ordered so that any prefix stays a balanced mix of intents — dish-specific
searches, ambience, service, value-for-money, and complaints — rather than, say,
ten dessert queries in a row. Re-sorting the file silently changes what every
sweep point measures.

Ids 1-10 are pinned as the latency workload because the figures recorded in
`benchmark.md` §1.4 come from exactly those ten.

### Why hand-written rather than sampled from the corpus

A query lifted out of a review trivially retrieves that review, which would
inflate context precision. These are written to resemble what a user would
actually type, not what the corpus already contains.

**Caveat worth keeping in mind:** they are not a native speaker's Thai, and they
carry no relevance judgements. That is why they support the reference-free RAGAS
metrics in §1.5 but do **not** satisfy the labelled eval set that
[`docs/part_1/benchmark.md`](../../docs/part_1/benchmark.md) §1.3 is blocked
on — recall, nDCG and MRR still need gold judgements, which is Phase 6 work.

### Loading

```python
import json
from pathlib import Path

rows = [json.loads(line) for line
        in Path("data/eval/thai_queries.jsonl").read_text(encoding="utf-8").splitlines()
        if line.strip()]
queries = [r["query"] for r in rows]
```

## `reviews_heldout_sample.jsonl`

100 real customer reviews for scoring the `assess` prompt (options 2+3 of
[`faithfulness_diagnosis.md`](../../docs/part_1/faithfulness_diagnosis.md)).
Each review goes into the prompt's `<review>` slot, and into the judge's
context, exactly as an operator would submit it.

| | |
|---|---|
| Source | `data/wongnai-corpus-master/review/review_dataset/test_file.csv`, the split that was **never ingested** |
| Seed | `SAMPLE_SEED = 20261019` in [`evaluation/heldout.py`](../../evaluation/heldout.py) |
| Pool | **6,195** of 6,203 non-empty rows. **8** were excluded first because their text exactly matches a row of `w_review_train.csv`, which is indexed |
| sha256 | `a023765acc0a36ae56a5890b849d5b16c675b63d6e6c5f98f416df50b37a743c` (sampled 2026-10-20). The first 12 hex chars are the `eval_set_sha` |
| Self-retrieval check | not yet run (R2) |

| Field | Meaning |
|---|---|
| `id` | 1-100, contiguous, stable. The order is the sample order |
| `text` | The review, verbatim -- leading whitespace and embedded newlines included |
| `review_id` | `reviewID` in `test_file.csv` |
| `source` | `test_file.csv#<review_id>` |

### Why the filter runs before the sample

A review that is already in the index retrieves itself at a score of ~1.0, which
makes `Precedent: recurring` trivially true. Filtering after sampling would
return fewer than 100 rows, or a different sample depending on how the gap was
refilled -- so the sample depends on the seed **and** the filter, and both are
recorded. Exact matching misses reworded near-duplicates; the R2 check
(`--check-retrieval`) and each run's `top1_score` cover those.

### Why there is no `rating` field

`test_file.csv` has no rating column -- only `reviewID;review`. The sample is
therefore **unstratified**, and its sentiment mix is whatever the draw produced.
Each run records the mix the generator reported (`sentiment_mix` in
`run_meta.json`). If it is mostly positive, Precedent and Actions are
under-exercised: that is a statement about the set, not about the prompt.

### Why the order matters

Notebook runs take the **first N** rows by `id` (N=10, then N=100), so a
re-sorted file silently changes what N=10 measures. The sampler writes with mode
`"x"` and refuses to overwrite: a re-sample under the same name is exactly the
silent change `eval_set_sha` exists to catch.

## `runs/`

One directory per run, created with `exist_ok=False` -- a run never writes into
another's directory, and nothing here overwrites the two fixed files above.

```
runs/
  assess-reviews_heldout-N<N>-<judge>-<UTC yyyymmdd-HHMM>/   notebook/eval_assess_grounding.ipynb
    responses.jsonl    one row per generation: id, review, response, response_extractive,
                       retrieved_contexts, prompt_set, top1_score
    dropped.json       ids whose extractive slice was empty, and why
    sweep.csv          faithfulness_full, faithfulness_extractive, context precision, n_extractive_count
    cost.json          projected and actual spend per stage
    run_meta.json      slug, git sha, judge, eval_set_sha, seed, sentiment_mix, self_retrieval_ids
    sweep.png
  loadtest-assess-<profile>-<UTC yyyymmdd-HHMM>/            tests/load/query_assess.k6.js
    k6_summary.json
```
